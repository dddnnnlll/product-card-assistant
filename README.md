# AI-помощник для товарных описаний

**[Открыть приложение на Streamlit](https://card-assistant-dddnnnlll.streamlit.app/)** · Доступ по паролю из сопроводительного сообщения.

Приложение на **Python + Streamlit**: по характеристикам прибора создаёт черновик B2B-карточки через бесплатную модель OpenRouter. Основной экран — четыре поля и кнопка «Создать описание». Демо без модели отсутствует.

## Быстрый запуск

Проверено на Python 3.11.9.

```powershell
git clone https://github.com/dddnnnlll/product-card-assistant.git
cd product-card-assistant
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Вставьте ключ в `.env` после `OPENROUTER_API_KEY=`. Создайте хеш пароля:

```powershell
.\.venv\Scripts\python.exe scripts/password_hash.py
```

Скопируйте полученный хеш в `.env` после `APP_PASSWORD_HASH=` (без кавычек). Исходный пароль передавайте проверяющему отдельно. Затем запустите:

```powershell
.\.venv\Scripts\python.exe -m streamlit run app.py --server.address 127.0.0.1
```

Откройте [localhost:8501](http://localhost:8501). На Windows можно также запустить `start.ps1`: при первом запуске он создаст окружение и установит зависимости. На macOS/Linux используйте `.venv/bin/python` вместо `.venv\Scripts\python.exe` и `cp .env.example .env` для копирования конфигурации.

## Как пользоваться

1. Заполните название, производителя, характеристики и исходное описание. Название обязательно; неизвестные сведения оставляйте пустыми.
2. Каждую характеристику пишите с новой строки: `Питание: 24 В`.
3. Нажмите **Создать описание**. Текст появится под формой.
4. Прочитайте результат и нажмите **Скачать описание**. Сохранится обычный `.txt`.

**Заполнить пример** подставляет учебный товар; текст по нему создаёт настоящая модель через тот же API. Другой пример, выбор модели и ввод ключа доступны в свёрнутых **Настройках**. Под результатом раскрываются характеристики, поисковые фразы, commercial-блок, проверки, цитаты и экспорт JSON/Markdown.

Ключ читается из окружения, локального `.env` или секретов Streamlit. Введённый в поле ключ используется только в сессии и не записывается на диск. `.env`, `.streamlit/secrets.toml`, окружение, кэши и `generated/` исключены из Git. Ключ в репозитории отсутствует. Команда локального запуска слушает только `127.0.0.1`; телеметрия Streamlit выключена.

## Публикация на Streamlit Community Cloud

В [Streamlit Community Cloud](https://share.streamlit.io/) выберите репозиторий `dddnnnlll/product-card-assistant`, ветку `main`, файл `app.py`, Python 3.11. В **Advanced settings → Secrets** задайте `OPENROUTER_API_KEY` и `APP_PASSWORD_HASH` по шаблону `.streamlit/secrets.toml.example`. Не добавляйте секреты в GitHub.

Без `APP_PASSWORD_HASH` доступ закрыт. До входа доступны только поле пароля и кнопка «Войти»; генерация и настройки скрыты. Пароль хранится как PBKDF2-SHA256-хеш со случайной солью и 600 000 итераций. Выход очищает данные текущей сессии. Это общий пароль для демонстрации: отдельных пользователей, восстановления доступа и глобального ограничения попыток нет. После смены хеша прежние сессии запрашивают вход заново.

## Бесплатная модель

По умолчанию: `nvidia/nemotron-3.5-super-vl:free` через [OpenRouter](https://openrouter.ai). [Создать API-ключ](https://openrouter.ai/settings/keys).

Приложение принимает только модели с `:free` и перед каждым запуском проверяет нулевые цены в публичном каталоге. В запросе также задан нулевой предел цены входных и выходных токенов. Платные модели, платные дополнения и автоматический переход на платную модель не используются.

Бесплатные варианты `:free` не требуют покупки кредитов или карты, но имеют общую квоту и ограничения доступности. По опубликованным условиям на момент проверки — 50 запросов в сутки и 20 в минуту; неудачные попытки тоже могут расходовать квоту. [Условия OpenRouter](https://openrouter.ai/collections/free-models/), [лимиты](https://openrouter.ai/docs/api_reference/limits).

Обычно карточка использует **3 запроса**: извлечение, написание, смысловая проверка. Одна исправляющая попытка включена по умолчанию; максимум **5 запросов**. При пустом описании извлечение пропускается. При конфликте работа останавливается после извлечения. Просмотр и скачивание не вызывают модель. Отдельные рассуждения модели отключены, чтобы не расходовать объём ответа на эту короткую задачу.

## Что возвращается

- SEO-заголовок до 70 символов.
- SEO-описание 800–1200 символов при достаточных данных.
- Структурированные характеристики с сохранением исходных значений.
- 3–5 уникальных поисковых фраз; частотность не проверяется.
- Краткий commercial-блок: кому подходит прибор и какую задачу решает.
- Предупреждения, источники фактов и результаты проверок.

Длина считается Python `len` по строке поля, с пробелами и переводами строк. При наличии минимум трёх подтверждённых свойств помимо названия и производителя границы описания обязательны. Если после одной правки длина или факты не проходят проверку, карточка блокируется с понятной ошибкой. Слишком длинный заголовок блокируется всегда.

Если данных мало, возвращается **частичный черновик**: `status=needs_information`, `requirements_met=false`. Он не выдаётся за полную карточку по ТЗ. Неизвестные переданные характеристики и отсутствующие назначение/аудитория отмечаются как «данных нет». При противоречиях приложение показывает оба значения и просит уточнить вход до генерации.

Все результаты имеют `needs_review=true`: перед публикацией их проверяет контент-менеджер. `requirements_met` отражает автоматические проверки формата, а `semantic_reviewed` — выполнение проверки моделью; эти поля не являются гарантией фактической точности.

## Как ограничиваются выдуманные сведения

1. Pydantic проверяет вход до обращения к модели.
2. Название, производитель и `specs` копируются в факты кодом с сохранением значений.
3. Явные фразы «предназначен для», «Кому подходит:» и характеристики с известными названиями дополнительно извлекаются кодом. Это сохраняет назначение, даже если модель неверно переписала цитату.
4. Модель извлекает другие факты из описания. Цитата должна присутствовать в исходнике, значение — в цитате. Допускаются только различия пробелов; в результат возвращается оригинальная запись. Неподтверждённые варианты исключаются.
5. Разные значения одинаковых полей считаются конфликтом; небольшой словарь синонимов помогает сопоставлению. Электрическое подключение не приравнивается к технологическому присоединению.
6. Автор получает только разрешённые факты и пишет блоки со ссылками на их ID. Схема отдельно ограничивает заголовок и описание; код повторно проверяет длину, ссылки, числа, распространённые единицы и повторяющиеся запросы.
7. Commercial-блок собирается кодом из явных полей назначения и аудитории. Назначение не выводится из названия прибора; при отсутствии сведений появляется просьба уточнить их.
8. Отдельный запрос к той же модели проверяет смысл: пары свойство–значение, назначение, ограничения, отрицания и неподтверждённые отрасли. При замечаниях допускается одна правка и повторная проверка. Неисправленный ответ блокируется.

Входные документы трактуются как данные. Промпты запрещают исполнять инструкции внутри них и добавлять сведения о материалах, совместимости, сертификатах, наличии, цене и доставке. Короткие дополнительные проверки блокируют неподтверждённые утверждения о продаже и подмену назначения словом «учебный».

Промпты находятся в `card_assistant/prompts.py`: `EXTRACT_SYSTEM`, `WRITE_SYSTEM`, `REVIEW_SYSTEM`. Структурированный вывод используется при поддержке моделью; иначе запрашивается JSON-объект и выполняется проверка приложением. JSON-схема обеспечивает структуру, но сама по себе не доказывает достоверность.

## Примеры и фактическая проверка

В предоставленном PDF нет полных данных двух обещанных товаров. По согласованию использованы **два вымышленных учебных товара**, а не характеристики реальной продукции:

| Вход | Реальный результат API | Заголовок | Описание | Поисковые фразы |
|---|---|---:|---:|---:|
| [Манометр](examples/manometer.json) | [Markdown](examples/live_manometer.md), [JSON](examples/live_manometer.result.json) | 57 | 805 | 4 |
| [Преобразователь](examples/transmitter.json) | [Markdown](examples/live_transmitter.md), [JSON](examples/live_transmitter.result.json) | 57 | 851 | 4 |

Проверены также [неполные данные](examples/incomplete.json) и [противоречие диапазонов](examples/conflict.json). Реальные результаты и статусы находятся в `examples/live_evaluation.json` и `examples/live_edge_checks.json`. Короткий результат для неполного ввода намеренно не считается выполнением требования 800–1200. Никакие значения учебных приборов нельзя использовать как паспорт реального товара.

## Запуск из JSON без браузера

```powershell
.\.venv\Scripts\python.exe -m card_assistant examples/manometer.json --output generated
```

Это тоже реальный вызов API. Результат сохраняется в JSON и Markdown. Можно передать `--model` с другим бесплатным ID.

Внутренний формат:

```json
{
  "name": "Название прибора",
  "manufacturer": null,
  "specs": {"диапазон измерений": "0–1,6 МПа", "питание": null},
  "description": "Фрагмент паспорта"
}
```

Название — непустая строка до 200 символов. Производитель и значения характеристик — строки до 300 символов или `null`. До 40 характеристик, описание до 12 000 символов, общий JSON до 60 000 байт UTF-8. Неизвестные поля, дубликаты JSON-ключей и неверные типы отклоняются. Числа передавайте строками вместе с единицами для сохранения исходной записи.

## Тесты и повторение живой проверки

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
```

Автоматические тесты не используют ключ и не расходуют квоту. Они проверяют ошибки ввода, пропуски, точные цитаты, конфликты, длину, смысловую проверку на контролируемых ответах, подмену единиц, бесплатный тариф, ошибки API, ограничение исправлений и обычную форму Streamlit. Подмены API находятся только в тестах и недоступны из приложения. GitHub Actions запускает проверку секретов и тесты без учётных данных.

Повторить проверку на настоящей модели (расходует бесплатную квоту):

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_live.py --edge-cases
```

Команда перезапишет результаты четырёх учебных сценариев и сводку. Без `--edge-cases` проверяются только два полных товара. `TEST_REPORT.md` описывает последний проверенный запуск, `requirements-tested.txt` — использованные прямые зависимости.

## Ограничения и улучшения

- Автор и смысловой проверяющий используют одну модель: ошибки могут совпасть. Проверки чисел и сигнатур также эвристические. Нужны экспертная проверка и более широкий размеченный набор.
- Цитата подтверждает происхождение текста, а не правильность интерпретации. Словарь синонимов и извлечение отрицаний не универсальны; возможны пропущенные или ложные конфликты.
- Минимальный объём невозможно честно получить для любого скудного ввода. В таком случае возвращается частичный результат или запрос уточнения, без выдумывания свойств.
- Бесплатный сервер может отвечать медленно или возвращать 429. HTTP-тайм-аут ограничивает ожидание сетевых данных, а не гарантирует общее время всей цепочки. Автоматических бесконечных сетевых повторов нет.
- В режиме API исходные сведения передаются OpenRouter и выбранному провайдеру. Для непубличной документации нужно учитывать их условия обработки данных.
- Нет массовой генерации, PDF-загрузки в форме, базы данных, отдельных учётных записей и CMS. Веб-интерфейс защищён общим паролем для демонстрации; CLI использует локальный API-ключ.

Дальнейшие улучшения: сравнение нескольких проверяющих, редактирование фактов до генерации, расширение тестового набора и пакетная обработка. Сопроводительный текст для сдачи — в `SUBMISSION.md`.
